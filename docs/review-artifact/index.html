Why this design

Controls before automation

  • 01Permission is explicit. A preflight shows engine, provider, model, reference version, tolerances and warnings before any file is processed.
  • 02Extraction is separate from approval. Completeness describes filled fields; validation and human review determine export readiness.
  • 03Exceptions stop safely. Missing identity, quantity, price, receipt or tax evidence stays held for correction.
  • 04The source stays visible. Reviewers compare the original document with editable values and provenance.

MVP success definition

Ready for a controlled pilot when…

  • 100%of processing starts have a recorded, confirmed rule plan.
  • 100%of exports have passed current reference rules and evidence confirmation.
  • 0provider keys are stored in browser storage or returned by state APIs.
  • 3exact output sheets share transaction numbers across a batch.

These are acceptance gates, not measured production performance. Pilot throughput and extraction accuracy baselines remain to be established.

Security posture

Data boundaries

  • Non-GET requests require a same-origin studio header.
  • Uploads are bounded by type, size and page/frame limits.
  • API keys stay encrypted server-side and clear from the form after save.
  • Local engine subprocesses do not receive provider secrets.
  • Claude Code receives extracted OCR text with tools disabled.
  • Originals and responses use no-store and restrictive browser headers.

Design choices

Decisions that shape the MVP

ChoiceWhyTrade-off
Local-first engine chainPreserves a useful path without sending invoice data outside the machine.Optional engines add installation weight and first-use model downloads.
Preflight token bound to rulesMakes provider, model, references and tolerances reviewable before processing.A changed rule invalidates the plan and requires another confirmation.
Exact reference matchingAvoids silently inventing item, route, receipt or tax decisions.Unclean master data becomes a visible hold rather than an automatic guess.
Optimistic revisionsPrevents one reviewer from overwriting a newer edit.Stale sessions must refresh and reapply changes.
Atomic batch exportKeeps transactions joined and avoids partial batch delivery.One invalid or stale invoice holds the entire selected batch.

Delivery sequence

From verified MVP to supplier rollout

Progress moves through evidence gates. Dates are set only after source mappings and pilot ownership are approved.

Phase 0 · NowWorking MVP

Prove the guarded workflow

Keep the current local workspace reproducible and verify its contracts with synthetic data.

  • Preflight confirmation on upload, retry and demo
  • Local engines and optional provider routing
  • Reference rules, evidence review and audit
  • Individual and multi-invoice three-sheet export
Exit: automated backend and browser contracts pass.
Phase 1 · NextPlanned

Map approved source masters

Build a distinct ingestion path for operational item, PO and receipt sources without placing private data in the repository.

  • Approve source-to-canonical mappings and owners
  • Represent store / warehouse location type explicitly
  • Reject target-output workbooks presented as masters
  • Reconcile identifiers, leading zeroes and currency precision
Exit: representative private samples import with signed-off counts and exceptions.
Phase 2 · PilotPlanned

Onboard a controlled supplier set

Start with a small, varied invoice cohort and measure manual effort rather than assuming automation quality.

  • Choose supplier layouts and language mix
  • Build and version known-layout templates
  • Measure field completeness and validation holds separately
  • Record reviewer time, correction types and failure causes
Exit: finance, buying, receiving and tax owners accept results and operating controls.
Phase 3 · CloudDeployment in progress

Deploy and govern on Firebase / GCP

Preserve the verified controls while moving identity, API execution and persistence into an approved cloud envelope.

  • Firebase Hosting and allowlisted Firebase Authentication
  • Cloud Run API with authenticated same-origin requests
  • Managed state, protected document storage and server-side secrets
  • Retention, region, backup, monitoring and support ownership
Exit: cloud auth, persistence, recovery and end-to-end acceptance pass without weakening local mode.

Working MVP

Verified implementation evidence

  • Processing gateBrowser automation proves no job starts before explicit preflight confirmation, and Cancel preserves the queue without sending the file.
  • Review gateUnconfirmed invoices are held in the UI and by the server export endpoint.
  • Batch integrityTwo reviewed invoices export atomically with transaction 1 and 2 joined across all three sheets.
  • Output contractDetails contains the exact six required columns and no helper/formula columns.
  • Secret handlingA unique key marker entered in the browser does not appear in local or session storage.
Live AI untested

Claims deliberately withheld

  • No production extraction accuracy or throughput benchmark.
  • No live OpenAI, Anthropic, ChatGPT or Claude quality comparison.
  • No guarantee of subscription eligibility, model access, latency or provider cost.
  • No confirmation that current supplier layouts are represented.
  • No production data residency, retention or service-level claim.
